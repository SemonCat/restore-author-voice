# Professional venue guides

Read recent human-written artifacts from the same venue when available. Match their register, length, headings, and conventional templates. Conventional containers are not AI evidence; filler inside them is.

## Shared checks

- Open with the reader's decision, result, or requested action.
- Keep length proportional to stakes and remove restated context.
- Commit to a judgment where the genre requires one; hedge only genuinely uncertain claims.
- Attach claims to real artifacts: versions, timestamps, links, commands, error text, code locations, or measurements with conditions.
- Keep formatting functional. Do not fill every template field or give every section equal weight.
- End when the content ends; delete generic recaps, future outlook, support-desk sign-offs, and reflex praise.
- Read rewritten sentences aloud. Correct but unsayable prose still fails.

## Venue routes

### Release notes and announcements

Put breaking changes and exact migration steps first. State user impact and the mechanism or artifact behind each claim. Match the repository's changelog format; do not inflate a patch release with marketing language, ceremonial introductions, or a roadmap conclusion.

### PR, issue, and review replies

Answer or give the verdict in the first sentence. Cite the exact code, commit, error, or documentation. State uncertainty cheaply, disagree plainly with a reason, and distinguish blocking findings from nits using the repository's convention. Thank people when the contribution warrants it, not as an automatic opener.

### Incident postmortems and RCA

Be blameless toward people and precise about mechanisms. Use absolute timestamps with timezone, include wrong turns, explain the code/config/query/race that failed, and state the causal chain you actually believe. Put measured impact before narrative. Action items need a concrete change, owner, and date when the source provides them; leave unknowns explicit.

### Tickets, work orders, and bug reports

Make the title state the outcome or defect. Include only context the assignee lacks, link canonical background, and give exact repro, expected versus actual behavior, scope boundary, and testable acceptance criteria. Empty or N/A beats filler.

### Technical articles and tutorials

Open at the real problem, observation, or number that forced the question. Spend words unevenly where the work became interesting. Include real dead ends, runnable code or an explicit sketch disclaimer, numbers with conditions, and a recommendation with the condition that would change it. If no lived incident exists, use the honest genre rather than fabricating one.
